# Layer 26 - Grounded Career Agent

Layer 26 creates a governed career-agent spine. It is not a generic chatbot and
does not make LLM-only recommendations. The agent can answer strategic career
questions, generate action plans, and use opt-in progress memory only when the
output remains grounded in structured platform evidence.

Layer 26A supports grounded answers for:

- `where_should_i_apply`
- `city_fit`
- `companies_to_watch`
- `strongest_market_strategy`
- `what_should_i_do_this_month`

Layer 26B adds grounded action planning for:

- `weekly_job_search_plan`
- `regional_targeting_plan`
- `company_research_plan`
- `internship_application_calendar`
- `networking_plan`

Layer 26C adds approval-gated tool preparation for:

- `reminder`
- `career_report_export`
- `watchlist_update_suggestion`
- `notification_preference`
- `outreach_message_draft`
- `application_prep_checklist`

`job_application_submission` is represented only as a blocked action type so
tests and API guardrails can prove autonomous applications remain prohibited.

Public API endpoints:

- `POST /career-agent/answers`
- `POST /career-agent/action-plans`

Protected user endpoints:

- `POST /me/career-agent/action-plans`
- `GET /me/career-memory`
- `PUT /me/career-memory`
- `DELETE /me/career-memory`
- `POST /me/career-agent/tools/preview`
- `POST /me/career-agent/tools/approve`
- `POST /me/career-agent/tools/reject`
- `GET /me/career-agent/tools`
- `GET /me/career-agent/tools/{tool_request_id}`

## Evidence Contract

Every returned recommendation must include at least one `evidence_refs` entry.
Every strategic action-plan step must also include evidence refs. Plan evidence
refs are copied from the validated 26A answer and are never generated from
free-form user memory or preferences.

Valid evidence refs are public-safe pointers to structured platform data such
as:

- canonical regions
- region market scores
- canonical companies
- company-region presence rows
- company-region hiring rows
- company-region entry-level rows
- stored opportunity records
- bounded forecast exports

User preferences are carried separately in `preference_snapshot`. Preferences
may affect ranking and explanation, but `counts_as_evidence` is always `false`
and preference data may not appear as an evidence ref.

The guardrail validator rejects:

- recommendations with no evidence refs
- strategic plan steps with no evidence refs
- opportunity recommendations whose opportunity IDs are not backed by stored
  opportunity evidence
- plan steps whose matched opportunity IDs are not backed by stored opportunity
  evidence
- evidence refs that treat user preferences as source evidence
- evidence refs that treat career memory as source evidence
- private/internal metadata leaks
- forecast recommendations without bounded uncertainty warnings
- forecast-backed plan steps without bounded uncertainty warnings

## Freshness Contract

Every answer includes:

- top-level `freshness`
- per-answer `source_freshness`
- per-recommendation `freshness`

Every action plan includes:

- top-level `freshness`
- plan `source_freshness`
- per-step `freshness`
- freshness warnings when evidence is stale, partial, or unknown

Freshness is derived from existing structured freshness metadata where present,
especially hiring and entry-level `freshness_expires_at` fields and active
opportunity expiry state. If freshness cannot be established, the answer must
say `unknown` or `partial`; unknown freshness is never treated as fresh.

Known stale, partial, or unknown freshness is surfaced in recommendation
limitations, plan risks, and API envelope warnings.

## Uncertainty Contract

Every answer and recommendation includes `uncertainty` with:

- confidence level
- confidence score when available
- uncertainty level
- reasons
- limitations
- `forecast_based`
- `bounded`

Every action plan and plan step also includes uncertainty metadata. Forecast
evidence may influence prioritization only as a bounded directional signal, not
as a certain hiring outcome.

Forecast-backed recommendations must carry forecast evidence refs, confidence
labels, and the warning that forecast evidence is a bounded directional signal,
not a certain outcome.

## Action Planning Contract

Action plans are generated by first producing a validated 26A career-agent
answer, then converting grounded recommendations into ordered plan steps. A
plan must include:

- plan type
- summary
- time window
- ordered steps
- milestone or outcome for each step
- evidence refs for strategic steps
- freshness metadata
- confidence and uncertainty metadata
- warnings for stale, incomplete, low-confidence, or forecast-backed inputs
- explicit `user_action_required` or `system_suggested` labels

Action plans must not invent:

- job openings
- application deadlines
- company facts
- city facts
- recruiter or hiring contacts
- hiring probabilities
- guaranteed outcomes

Planning checkpoints are not application deadlines. Users must verify any real
application timing against official sources before acting.

## Progress Memory Contract

Career memory is private user context. It is off by default and no memory may
be saved without explicit user permission. Supported categories are:

- `saved_companies`
- `target_regions`
- `applied_roles`
- `preferred_industries`
- `rejected_markets`
- `career_constraints`
- `preferred_role_types`

Each category has a separate permission record. Memory entries are scoped to the
current user, category, and value. Memory can be edited by replacing category
entries or deleted by category, entry ID, or full clear.

Memory may personalize action plans only when the relevant category is enabled
and personalization is allowed. Rejected markets and applied roles influence
plans only under that permission. Memory is always `user_provided`,
`private`, and `counts_as_evidence: false`.

Career memory does not appear in public routes or public reports and is not
included in the existing user export payload. Public action plans are stateless;
the memory-backed plan route is protected under `/me`.

## Tool Approval Contract

Career-agent tools are safe preparation flows, not autonomous execution. Every
tool preview includes:

- tool type
- proposed action summary
- user-visible preview payload
- evidence refs when the action is grounded in strategy or product intelligence
- freshness metadata
- uncertainty and warnings
- approval requirement and action boundary
- current status
- privacy classification
- user scope for protected records
- audit events for preview, approval, rejection, or blocked states

Approval is required for actions that would change user state, create a
reminder, export user-specific data, update watchlists, create notification
preferences, contact another party, or submit an application. Layer 26C records
approval/rejection state but does not claim reminder, export, notification,
watchlist, outreach, or application runtime execution unless a real backend
runtime exists.

Outreach can be drafted as a read-only preparation action. Sending outreach is
blocked. Application-prep checklists are read-only and must not imply that the
system applied, submitted materials, contacted employers, or guaranteed an
outcome. Deadlines may appear only when grounded in trusted opportunity records.

Career report export previews are public/export-safe by default. Private memory
is excluded unless the user explicitly requests inclusion, and public payloads
still mark private memory as redacted.

## Anti-Fabrication Rules

The agent must not fabricate job openings. For `where_should_i_apply`, a
recommendation can reference a specific application target only when a stored
active verified or source-checked opportunity record exists.

When no verified opportunity record exists, the agent may return strategic
market or company guidance, but it must warn that no stored verified
opportunity record is attached and that the user must verify current openings
manually.

Layer 26 does not:

- apply to jobs or submit resumes
- mutate watchlists without explicit approval and a real runtime
- send outreach or contact employers
- create reminders without explicit approval and a real runtime
- create notification rules without explicit approval and a real runtime
- export user-specific reports without explicit approval and a real runtime
- scrape live listings
- use paid/partner status as a ranking boost
- use memory as evidence

## Redaction Rules

Career-agent payloads must not expose private/internal review notes, raw source
refs, fact-source-link IDs, admin metadata, private metadata, or internal
formula weights. Opportunity partner and paid-partner disclosures may be shown,
but internal review notes remain private.

Tool previews and export previews follow the same public/private separation.
Protected tool records are user-scoped and are denied from public-demo routes.
Frontend panels render backend tool status only and must not fake execution
success when the backend reports only `approved`, `rejected`, `blocked`, or a
read-only preview status.

## Current Limitations

Layer 26 is deterministic over available platform data. Progress memory is
limited to explicit category-scoped user context and does not implement
conversation memory. Layer 26C creates durable tool preview/approval records,
but reminder scheduling, notification delivery, file export generation,
watchlist mutation, outreach sending, and job application submission are not
wired as runtime integrations. Recommendation, plan, and tool-preview quality
depends on available canonical scores, opportunity records, historical exports,
freshness metadata, and confidence labels.
